## 3.6 Development Procedure

The engineering workflow of the Modular Adaptive Data Node (MADN) was divided into five sequential phases: hardware assembly, software environment configuration, daemon development, machine learning optimization, and mechanical fabrication. This section delineates the step-by-step development procedure executed to construct the prototype.

---

### 3.6.1 Hardware Assembly and Circuit Integration

The hardware tier construction was divided between the edge node microcontrollers and the central orchestrator hub:

1.  **Microcontroller Prep & Stacking**:
    *   Using a temperature-controlled soldering station set to 350°C, 2x20-pin male short plug headers (Adafruit Product 5584) were soldered directly to the Raspberry Pi Pico W GPIO rails, ensuring uniform pin vertical alignment.
    *   2x20-pin female socket headers (Adafruit Product 5583) were soldered onto the Adafruit Terminal PiCowbell (Product ID: 5904).
    *   The Pico W was stacked onto the PiCowbell by matching the male headers to the female socket headers, creating a stable mechanical joint and routing all pins to the spring-loaded screw terminals.
2.  **Edge Telemetry and User Interface Wiring**:
    *   The capacitive soil moisture sensor was connected via a three-wire cable to GP26 (ADC0), Ground, and the 3.3V OUT pin.
    *   The DHT22 sensor data pin was wired to GP15 with an external 4.7kΩ pull-up resistor connected to 3.3V to prevent signal floating.
    *   The HC-SR501 PIR sensor signal pin was routed to GP14, and powered from the boosted 5V VBUS rail.
    *   The HC-SR04 ultrasonic sensor was connected with the trigger pin to GP16 and the echo pin to GP17, powered by the 5V VBUS rail.
    *   The ST7735 SPI TFT display SPI lines (SCK, MOSI, CS, DC, RESET) were wired to GP18, GP19, GP20, GP21, and GP22 respectively.
    *   Three tactile push-buttons were wired between GP10, GP11, GP12, and local Ground pins.
3.  **Power Delivery Integration**:
    *   A TP4056 charger and step-up protection module was connected to a 3.7V 18650 Li-Ion cell.
    *   The boosted 5V output terminals of the TP4056 board were routed via a JST-PH 2.0 connector directly to the Pico W VBUS (Pin 40) and Ground pins to power the microcontroller and 5V sensors.
4.  **Central Vault Hub Setup**:
    *   The active cooling dual-fan shield was mounted onto the Raspberry Pi 4 CPU and SoC blocks.
    *   The low-power portable projector and active cooling fan were connected to the Pi 4's USB and GPIO power pins.
    *   A standard 5V USB-C power supply (PSU) was connected to the USB-C port of the Pi 4. A portable 5V USB power bank was prepared as a swappable alternative during grid failures.

---

### 3.6.2 Software Stack and Local Environment Configuration

The software deployment involved flashing edge devices, installing the server OS, and setting up offline local databases:

1.  **Edge Node Firmware Deployment**:
    *   The Pico W was booted in USB-mass-storage mode (holding the BOOTSEL button while plugging it into a PC).
    *   The stable MicroPython `.uf2` firmware file (v1.20 or later) was dragged and dropped onto the volume to flash the microcontroller.
2.  **Central Hub Operating System Installation**:
    *   The headless minimal ARM64 image of Kali Linux was flashed to the 128GB High-Endurance MicroSD card using the Raspberry Pi Imager utility on an external PC.
    *   The card was inserted into the Raspberry Pi 4, which was booted into a command-line interface. SSH keys and local user accounts were configured over a temporary Ethernet connection.
3.  **Offline Access Point and Broker Configuration**:
    *   `hostapd` and `dnsmasq` packages were installed and configured on the Pi 4. The wireless interface (`wlan0`) was assigned a static local IP address (`192.168.4.1`) and configured to project a local Wi-Fi Access Point (SSID: `MADN-Vault-Local`) with DHCP leasing IPs from `192.168.4.10` to `192.168.4.150`.
    *   The Mosquitto MQTT broker was installed on the Pi 4. The configuration file was set to allow anonymous connections on port `1883` over the local subnet.
4.  **Local Databases and Visualization Services**:
    *   InfluxDB (v2.x) was installed on the Pi 4. An initial bucket named `MADN_Telemetry` was initialized with default retention policies set to prevent excessive storage expansion.
    *   SQLite was installed to store local transactions.
    *   Grafana was installed, added InfluxDB as a data source via Flux query integration, and configured to autostart on system boot.

---

### 3.6.3 Embedded Scripting and Backend Daemon Scripting

Custom scripts were written to run continuously as headless daemons on the central hub and as sensor sampling routines on the edge nodes:

1.  **MicroPython Logic (Edge Node)**:
    *   A custom script (`main.py`) was written to run on boot. The script utilizes the `network` library to establish connection to the `MADN-Vault-Local` Wi-Fi AP.
    *   Inside the main execution loop, GP26 is polled to read soil moisture voltage, and the DHT22 library is called to poll temperature and humidity. An arithmetic moving-average filter of 5 samples is applied to the values.
    *   The filtered values are formatted into a JSON payload and published to the Mosquitto broker via the `umqtt.simple` package under the topic `madn/node1/telemetry`.
    *   The ST7735 driver is utilized to print moisture and temperature stats directly to the local edge display.
    *   Digital interrupt lines are bound to GP14 (PIR) and GP16/17 (Ultrasonic). Trigger events immediately dispatch high-priority JSON payloads to the topic `madn/node1/security`.
2.  **Security Event Daemon (Pi 4 Hub)**:
    *   A Python daemon script was written to subscribe to `madn/+/security`. When a trigger payload is intercepted, the daemon appends the timestamp, node ID, and status to the SQLite database ledger and updates a local alerts status file.
3.  **Commerce POS Daemon (Pi 4 Hub)**:
    *   A Python SocketServer was scripted to open an RFCOMM socket port (Channel 1) on the local Bluetooth stack (`hciconfig hci0 up`) and a WebSocket port on port `8080`.
    *   The server listens for JSON checkout payloads containing merchant ID, customer token details, and totals. It queries the local SQLite transaction database to validate balances and commits transaction logs locally using ACID transaction locks.

### 3.6.4 Predictive Modeling and TensorFlow Lite Quantization

To enable the local-first determination of watering requirements without cloud dependencies, a localized machine learning workflow was established:

1.  **Data Collection and Model Training**:
    *   A training dataset was compiled containing DHT22 climate parameters (ambient temperature, relative humidity) and capacitive soil moisture values, paired with binary labels indicating whether irrigation was required (1) or not (0).
    *   A dense feed-forward neural network was built in TensorFlow/Keras on a workstation, consisting of an input layer (3 features: soil moisture, temperature, humidity), two hidden layers (16 and 8 units with ReLU activation), and a single sigmoid output layer. The model was trained using binary cross-entropy loss.
2.  **Quantization and FlatBuffer Conversion**:
    *   To fit the processing limits of the Pi 4 and reduce runtime overhead, the Keras model (`.h5`) was converted using the TensorFlow Lite Converter.
    *   Post-training dynamic range quantization was applied to compress the model weights from floating-point values to 8-bit integers, reducing the final file size to less than 15KB.
    *   The quantized model was saved as a FlatBuffer binary file (`watering_model.tflite`).
3.  **Local Inference Integration**:
    *   The flatbuffer model was copied onto the Pi 4.
    *   A scheduler script on the Pi 4 initializes the TensorFlow Lite Interpreter runtime, loads `watering_model.tflite`, allocates tensors, and executes inferences on the latest cached InfluxDB telemetry data to write prediction labels back to the time-series database.

---

### 3.6.5 Parametric Modeling and Mechanical Fabrication

Custom mechanical protection was modeled and fabricated to secure the prototype against dust and moisture:

1.  **Parametric 3D CAD Modeling**:
    *   Using FreeCAD (v0.20+), parameter sheets were defined containing clearances for the Raspberry Pi Pico W, the stacked PiCowbell breakout terminal, the TP4056 module, and the 18650 cell.
    *   A snap-fit weatherproof enclosure casing was designed, featuring interlocking mating lips to achieve an IP65 protection rating, internal mounting standoffs, and ventilation ducts aligned with active fan exhaust pathways.
2.  **Slicing and G-code Export**:
    *   The 3D model designs were exported as STL files and imported into an open-source slicing software tool (PrusaSlicer).
    *   Slicing parameters were configured: layer height of 0.2mm, infill density of 20% with a gyroid pattern for structural integrity, and 3 shell perimeters to enhance waterproof properties.
3.  **Extrusion Printing**:
    *   PETG (Polyethylene Terephthalate Glycol) filament was loaded into a 3D printer. The nozzle was heated to 240°C and the print bed to 80°C.
    *   The enclosures were extruded, cooled, and post-processed by clearing support interfaces, after which the hardware shields and microcontroller boards were mounted inside.
